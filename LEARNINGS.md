## Accepted

- [A-1] Pi 1.4.0 exposes `ctx.getContextUsage(): { tokens: number|null; contextWindow: number; percent: number|null } | undefined`; `tokens` is a *projection-based estimate*: last trustworthy assistant usage plus chars/4 estimation of trailing messages, and is `null` after compaction until a new assistant response. evidence: dist/core/extensions/types.d.ts:197,248; dist/core/agent-session.js getContextUsage(); core/compaction/compaction.d.ts. confidence: high. adopted: yes (basis of the measurement adapter).
- [A-2] `turn_end` and `agent_before_settle` are the actionable boundaries; while streaming, `pi.sendMessage(msg, {triggerTurn:false})` defers the append to end of turn, so alerts never interrupt an in-flight tool call. evidence: docs/extensions.md (BoundaryState), dist/core/agent-session.js sendCustomMessage(). confidence: high. adopted: yes (all alerts use this path).
- [A-3] Automatic compaction is already disabled here (`/home/john/.sushibeta/pi/settings.json`: `compaction.enabled=false`, `reserveTokens=20000`); the guard must therefore never rely on compaction and never call `ctx.compact()`. evidence: settings.json, config.yml; docs/settings.md. confidence: high. adopted: yes (test R10 asserts zero compact calls).
- [A-4] Node 26.12.1 runs TypeScript test files natively (`node --test`, type-stripping): `private` class members and `import type` are erased; enums/parameter properties are forbidden. This allows dependency-free tests of the extension's pure modules. evidence: `node --test` green; `process.features.typescript === "strip"`. confidence: high. adopted: yes (test harness design).
- [A-5] Pi 1.4.0 session replacement (`newSession`/`switchSession`/`fork`) invalidates the old extension context; only plain data may be carried across, via the `withSession(ReplacedSessionContext)` callback. evidence: docs/extensions.md, types.d.ts ReplacedSessionContext; examples/extensions/handoff.ts. confidence: high. adopted: deferred to Phase 2 design notes in PROTOCOL.md.
- [A-6] The Phase 1 validator could not detect a stale checkpoint: `validateFile` only checks section headings, managed blocks carried no content fingerprint, and `readRecoveryBundle` preferred the block's next action over newer manual prose (`nextFromCheckpoint ?? nextFromHandoff`). Reproduced on the real files: legacy block (session 01a1865b) said "live walkthrough", prose said "Phase 1 complete"; both validated, stale one won. Fixed by schema-v2 source hashes + prose-first precedence + stale/corrupt/missing/current classification (`validateCheckpoint`). evidence: /tmp repro scripts (pre-fix), test/freshness.test.ts (8 tests), real Pi RPC notifications post-fix. confidence: high. adopted: yes (PROTOCOL §2.1).
- [A-7] Single-slot `.pi-guard/state.json` allowed cross-session overwrite: the audit session (01a18668) replaced the checkpoint session's (01a1865b) runtime snapshot at its `session_start` (`persistState()`), and live monitoring during Phase 1b re-confirmed the auto-loaded guard rewrites the file every turn of its session. Fixed with per-session files `sessions/<sessionId>.json` (v2), newest-wins v1 migration, per-session corruption quarantine, retention pruning. evidence: pre-fix file contents vs HANDOFF session id; test/sessions.test.ts S1–S4; real migration on `.pi-guard/`. confidence: high. adopted: yes (PROTOCOL §2.2).
- [A-8] "Read-only" by instruction is not read-only: an audit session told not to edit project files still mutated the tree because Pi auto-loads trusted project extensions (`.pi/extensions/`) and the guard wrote runtime state on `session_start`. A genuinely immutable snapshot requires OS-level enforcement (read-only mount/permissions), which the guard does not provide. New `readOnly` audit mode (config/env/`--guard-readonly`) gives tree-zero-writes; state can live outside via `CONTEXT_GUARD_STATE_DIR`. Verified live: RPC audit session on a temp tree copy left it byte-for-byte unchanged. evidence: audit-session state.json writes; README §Read-only audit mode; test/sessions.test.ts S6/S6b/S7. confidence: high. adopted: yes (PROTOCOL §2.3).
- [A-9] Mock-only tests can miss real-runtime defects: `--guard-readonly` crashed with "Assignment to constant variable" in the real jiti/pi runtime while all 55 mock tests passed, because `createMockPi().getFlag` always returned `undefined` and never executed the flag branch. e2e verification against the real runtime is part of the gate, and mocks must be extended when they mask code paths (getFlag now supports flags). Also: RPC-mode commands sent immediately at startup can race ahead of `session_start` ("not initialized") — drive RPC tests with a warm-up delay. evidence: /tmp/rpc-out*.jsonl `extension_error` record; S6b now covers the flag path. confidence: high. adopted: yes.

## Proposed

- [P-1] Phase 2 renewal could reuse the built-in example pattern (`examples/extensions/handoff.ts`): `ctx.newSession({parentSession, withSession})` + `waitForIdle`, with the handoff prompt composed from GOAL/HANDOFF instead of an LLM summary (keeps renewal deterministic and cache-cheap). evidence: example source. value: removes lossy compaction entirely. cost: one extra session file; needs Phase 2 tests. confidence: medium. status: proposed.
- [P-2] Alert delivery via `turn_end` BoundaryResult `entries` (instead of deferred `sendMessage`) might place alerts more precisely; untested against 1.4.0 entry-validation rules. evidence: docs/extensions.md boundary table. value: small. cost: risk of malformed drafts. confidence: low. status: proposed.
- [P-3] Recovery audits of this project should run with `CONTEXT_GUARD_READONLY=1` (or `--guard-readonly 1`) plus an external `CONTEXT_GUARD_STATE_DIR`, and explicitly via `pi -e <path>` rather than relying on project trust, so an audit observes rather than perturbs the snapshot. Not yet exercised as a full scripted audit procedure. evidence: A-8/A-9 mechanisms now exist and are tested. value: audits become reproducible and non-mutating. cost: trivial env wiring in the audit prompt. confidence: high (mechanism), medium (procedure adoption). status: proposed.
- [P-4] Persist the checkpoint fingerprint (`current` at write time) plus a monotonic checkpoint counter in the per-session state so Phase 2 renewal can refuse to spawn a successor session from a stale checkpoint and can audit which checkpoint seeded a session. evidence: `checkpointFreshness` audit field already persisted (v2 state). value: closes the renewal trust loop. cost: small state + validation addition in Phase 2. confidence: medium. status: proposed.
- [P-5] Concurrency: per-session state files + atomic tmp/rename *should* make parallel sessions safe (each writer owns one file; readers are per-id), but this is untested with real simultaneous processes — Node test runner is single-process and serial. Proposal: a two-process integration check (e.g. two `pi --mode rpc` instances racing on one temp tree) before trusting Phase 2 with parallel renewal. evidence: none yet — explicitly NOT claimed. value: removes the main open risk of auto-renewal. cost: one brittle-by-design integration script; keep out of the deterministic suite. confidence: low until run. status: proposed.

## Tool / procedure knowledge

- Pi 1.4.0 loads project extensions from `.pi/extensions/` (dir with index.ts) only after project trust; `pi --extension <path>` (`-e`) loads explicitly regardless — use `-e` during development. evidence: docs/configuration.md, docs/extensions.md, `pi --help`. confidence: high.
- `pi.appendEntry(customType, data)` persists session state that never enters model context — used as the alert audit trail. confidence: medium (documented; audit path exercised in mock tests only).
- Pi extension flags registered via `pi.registerFlag` require an explicit value on the CLI (`--guard-readonly` alone errors; `--guard-readonly 1` works); unknown/unset flags may throw from `pi.getFlag` — keep the try/catch wrapper. In `--mode rpc`, extension commands dispatched before `session_start` completes see an uninitialized extension — add a warm-up delay in scripted RPC tests. evidence: real Pi 1.4.0 RPC runs (rpc-err.txt, rpc-out jsonl). confidence: high.

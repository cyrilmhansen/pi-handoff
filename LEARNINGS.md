- [A-17] Pi 1.4.0 session-replacement semantics, source-verified in the installed dist (Phase 2 increment A):
  1. **Where the renewal primitives live**: `waitForIdle/newSession/switchSession/fork/reload` exist ONLY on `ExtensionCommandContext` (types.d.ts:290-335), i.e. in command handlers. Event handlers get plain `ExtensionContext` — renewal cannot be initiated directly from `turn_end`/`tool_call`; the agent must invoke a command (`/handoff renew`) — this matches PROTOCOL §6 ("explicitly triggered, never while a tool call is in flight").
  2. **`newSession()` ordering** (agent-session-runtime.js:147-174): emits `session_before_switch {reason:"new"}` (cancellable via handler return `{cancel:true}` — agent-session-runtime.js:80-89) → `teardownCurrent` = `session.abort()` + `session_shutdown {reason:"new", targetSessionFile}` + `dispose()` → `createRuntime({sessionStartEvent:{type:"session_start",reason:"new",previousSessionFile}})` → optional `setup(sessionManager)` + `refreshContext()` → `finishSessionReplacement`: `rebindSession` (rpc-mode.js:225-240 rebinds the RPC host and binds extension actions) → `withSession(nctx)` → returns `{cancelled}` (agent-session-runtime.js:115-121; createReplacedSessionContext at agent-session.js:3403).
  3. **Fresh context, no replay, compaction untouched**: new session starts with an empty transcript; the guard's no-compaction invariant is unaffected (`session_before_compact` is never on the renewal path).
  4. **Same `pi` module instance in the successor session**: main.js `createRuntime` (~line 590-700) rebuilds services per replacement, but jiti caches the extension module (jiti-loader.js uses the runtime jiti instance; no `moduleCache:false`), so `export const`/top-level `let` in index.ts persist across replacement; the factory is re-invoked against the NEW session's runtime (loader.js:560 `runtime ?? createExtensionRuntime()`), and our guard's `session_start` handler fully rebuilds `g` from files + `sessions/<newId>.json`. Renewal counters that must survive the transition therefore live in module-scope or in the persisted per-session state files — not in `g`.
  5. **Invalidation**: the old runner is invalidated on `dispose()` (agent-session.js:1022): using the captured command `ctx` after `await ctx.newSession(...)` throws "This extension ctx is stale…"; all post-switch work and reporting MUST happen inside `withSession(nctx)`.
  6. **Starting inference**: `nctx.sendMessage(msg,{triggerTurn:true})` on an idle new session executes `_startRun` and AWAITS it (`sendCustomMessage`, agent-session.js:1844-1872; while streaming the same options instead steer/followUp). So awaiting the send inside `withSession` blocks `newSession()` (and the initiating command) until the successor's first turn finishes — see O-1.
  evidence: installed 1.4.0 dist sources cited above; matches docs/extensions.md + examples/extensions/handoff.ts (which uses `parentSession` + `withSession`, TUI-only draft editing — we replace the draft step with a deterministic triggered message). confidence: high (source), pending live RPC confirmation (O-1/O-2). adopted: basis of P-6.

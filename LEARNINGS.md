- [A-17] Pi 1.4.0 session-replacement semantics, source-verified in the installed dist (Phase 2 increment A):
  1. **Where the renewal primitives live**: `waitForIdle/newSession/switchSession/fork/reload` exist ONLY on `ExtensionCommandContext` (types.d.ts:290-335), i.e. in command handlers. Event handlers get plain `ExtensionContext` — renewal cannot be initiated directly from `turn_end`/`tool_call`; the agent must invoke a command (`/handoff renew`) — this matches PROTOCOL §6 ("explicitly triggered, never while a tool call is in flight").
  2. **`newSession()` ordering** (agent-session-runtime.js:147-174): emits `session_before_switch {reason:"new"}` (cancellable via handler return `{cancel:true}` — agent-session-runtime.js:80-89) → `teardownCurrent` = `session.abort()` + `session_shutdown {reason:"new", targetSessionFile}` + `dispose()` → `createRuntime({sessionStartEvent:{type:"session_start",reason:"new",previousSessionFile}})` → optional `setup(sessionManager)` + `refreshContext()` → `finishSessionReplacement`: `rebindSession` (rpc-mode.js:225-240 rebinds the RPC host and binds extension actions) → `withSession(nctx)` → returns `{cancelled}` (agent-session-runtime.js:115-121; createReplacedSessionContext at agent-session.js:3403).
  3. **Fresh context, no replay, compaction untouched**: new session starts with an empty transcript; the guard's no-compaction invariant is unaffected (`session_before_compact` is never on the renewal path).
  4. **Same `pi` module instance in the successor session**: main.js `createRuntime` (~line 590-700) rebuilds services per replacement, but jiti caches the extension module (jiti-loader.js uses the runtime jiti instance; no `moduleCache:false`), so `export const`/top-level `let` in index.ts persist across replacement; the factory is re-invoked against the NEW session's runtime (loader.js:560 `runtime ?? createExtensionRuntime()`), and our guard's `session_start` handler fully rebuilds `g` from files + `sessions/<newId>.json`. Renewal counters that must survive the transition therefore live in module-scope or in the persisted per-session state files — not in `g`.
  5. **Invalidation**: the old runner is invalidated on `dispose()` (agent-session.js:1022): using the captured command `ctx` after `await ctx.newSession(...)` throws "This extension ctx is stale…"; all post-switch work and reporting MUST happen inside `withSession(nctx)`.
  6. **Starting inference**: `nctx.sendMessage(msg,{triggerTurn:true})` on an idle new session executes `_startRun` and AWAITS it (`sendCustomMessage`, agent-session.js:1844-1872; while streaming the same options instead steer/followUp). So awaiting the send inside `withSession` blocks `newSession()` (and the initiating command) until the successor's first turn finishes — see O-1.
  evidence: installed 1.4.0 dist sources cited above; matches docs/extensions.md + examples/extensions/handoff.ts (which uses `parentSession` + `withSession`, TUI-only draft editing — we replace the draft step with a deterministic triggered message). confidence: high (source), pending live RPC confirmation (O-1/O-2). adopted: basis of P-6.

## Proposed

- [P-8] Model-triggered renewal via a guard-registered tool: the tool's `execute()` performs the GATES + checkpoint + attest synchronously, then **fire-and-forgets** `pi.sendUserMessage("/handoff renew go", { expandPromptTemplates: true })` and returns its tool_result immediately. Reason: `newSession` is command-context-only (A-17.1), and A-19 shows command dispatch works mid-turn — but a tool that AWAITED the renewal would deadlock: `waitForIdle()` inside the command waits for the agent run, and the agent run is blocked on this tool's result. Fire-and-track lets the turn finish; the command handler then proceeds at settle. evidence: A-19 (dispatch verified in source); deadlock reasoning NOT yet executed live. value: true autonomous A→B→C without human keystrokes, inside one pi process. cost: one small tool + pending-marker + stop flag. confidence: medium (must be proven in increment C). status: **ACCEPTED — live-verified in increment C (A-23): the model called `handoff_renew`, the dispatch fired mid-turn, no deadlock, the switch happened after settle.**

- [P-1] Phase 2 renewal could reuse the built-in example pattern (`examples/extensions/handoff.ts`): `ctx.newSession({parentSession, withSession})` + `waitForIdle`, with the handoff prompt composed from GOAL/HANDOFF instead of an LLM summary (keeps renewal deterministic and cache-cheap). evidence: example source. value: removes lossy compaction entirely. cost: one extra session file; needs Phase 2 tests. confidence: medium. status: proposed.
- [P-2] Alert delivery via `turn_end` BoundaryResult `entries` (instead of deferred `sendMessage`) might place alerts more precisely; untested against 1.4.0 entry-validation rules. evidence: docs/extensions.md boundary table. value: small. cost: risk of malformed drafts. confidence: low. status: proposed.
- [P-3] Recovery audits of this project should run with `CONTEXT_GUARD_READONLY=1` (or `--guard-readonly 1`) plus an external `CONTEXT_GUARD_STATE_DIR`, and explicitly via `pi -e <path>` rather than relying on project trust, so an audit observes rather than perturbs the snapshot. Not yet exercised as a full scripted audit procedure. evidence: A-8/A-9 mechanisms now exist and are tested. value: audits become reproducible and non-mutating. cost: trivial env wiring in the audit prompt. confidence: high (mechanism), medium (procedure adoption). status: proposed.
- [P-4] Persist the checkpoint fingerprint (`current` at write time) plus a monotonic checkpoint counter in the per-session state so Phase 2 renewal can refuse to spawn a successor session from a stale checkpoint and can audit which checkpoint seeded a session. evidence: `checkpointFreshness` audit field already persisted (v2 state). value: closes the renewal trust loop. cost: small state + validation addition in Phase 2. confidence: medium. status: proposed.
- [P-6] Phase 2 renewal design (from the increment-A API audit, A-17): implement renewal INSIDE the `/handoff` command handler (`/handoff renew`), since `waitForIdle/newSession` exist only on `ExtensionCommandContext`. Sequence: gate on `renewAuthorization()` → `await ctx.waitForIdle()` → final checkpoint+attest → `ctx.newSession({ parentSession: ctx.sessionManager.getSessionFile(), withSession })`; `withSession(nctx)` sends the deterministic recovery instruction as a custom message (`customType:"context-guard-recovery"`) via `nctx.sendMessage(..., { triggerTurn: true })` — fresh context, no transcript replay, no compaction. Guard module state survives replacement (loader cache reuse), so the guard must re-init on `session_start` reason `"new"` (already does; should also record `previousSessionFile` + parent session id in the per-session state as the renewal audit trail, P-4). AVOID `await`ing the triggerTurn send inside `withSession` until the turn completes — that would block `newSession()` for the whole first turn; fire-and-track with a completion callback instead (open question O-1). Renewal must be config-gated (`autoRenew`-style, default off), bounded (`maxRenewals`), idempotent per checkpoint-id, and cancellable via a `session_before_switch` handler returning `{cancel:true}`. evidence: A-17. value: satisfies PROTOCOL §6 with Pi's own primitives, no external orchestrator. cost: ~1 config block + 1 command subcommand + ~150 lines. confidence: medium-high (mechanics source-verified; live RPC execution untested — O-1/O-2). status: **ACCEPTED — live-verified in increment C (A-23): operator hop 2 switched sessions; fire-and-track recovery settled O-1.**

## Tool / procedure knowledge

- Pi 1.4.0 loads project extensions from `.pi/extensions/` (dir with index.ts) only after project trust; `pi --extension <path>` (`-e`) loads explicitly regardless — use `-e` during development. evidence: docs/configuration.md, docs/extensions.md, `pi --help`. confidence: high.
- `pi.appendEntry(customType, data)` persists session state that never enters model context — used as the alert audit trail. confidence: medium (documented; audit path exercised in mock tests only).
- Pi extension flags registered via `pi.registerFlag` require an explicit value on the CLI (`--guard-readonly` alone errors; `--guard-readonly 1` works); unknown/unset flags may throw from `pi.getFlag` — keep the try/catch wrapper. In `--mode rpc`, extension commands dispatched before `session_start` completes see an uninitialized extension — add a warm-up delay in scripted RPC tests. evidence: real Pi 1.4.0 RPC runs (rpc-err.txt, rpc-out jsonl). confidence: high.
